# M6 首次上线与手动发布

日期：2026-10-12。目标是香港 Ubuntu 22.04.5 LTS、x86_64、2 核 2GB；用户已验证 Docker hello-world。Console/API：apm.revengedog.online；Demo：demo.revengedog.online。原上海 / OpenCloudOS 配置不再使用。

## 1. 本轮交付与边界

已新增平台生产容器、Caddy HTTPS 入口、生产资源限制和手动 Deploy platform 工作流。推送仍只触发 CI；手动发布需要完整 commit SHA，流程检查该 SHA 属于 main 且最新 push CI 成功。

第一轮只部署 Console / API / MySQL。Demo 在创建实际生产监控应用后单独发布，本轮没有 Demo 自动发布工作流，不要把平台上线当成完整 M4 线上闭环已经通过。

没有通过聊天连接服务器，也没有提交 / 推送本轮代码。以下是操作者要完成的服务器和 GitHub 配置，不是已经执行的操作。

## 2. 文件与运行方式

| 文件 | 用途 |
| --- | --- |
| deploy/server.Dockerfile | 运行 CI 已打包的 Java 21 JRE 应用，非 root 用户 |
| deploy/web.Dockerfile | 只包含构建后的 Console 和 Caddy，不包含 Demo 私有 Map |
| deploy/Caddyfile | 自动 HTTPS、同源 /api 代理、SPA 刷新和私有文件 404 |
| deploy/compose.production.yml | 单机生产服务、内网 MySQL、持久卷、日志 / 内存限制 |
| deploy/.env.production.example | 生产环境文件模板，不是真实凭证 |
| deploy/deploy-platform.sh | 串行发布、备份、拉取固定 digest、启动及 HTTPS 检查 |
| .github/workflows/deploy-platform.yml | CI 验证 → runner 构建并推送 GHCR → SSH 发布 |
| deploy/check-web.sh | 容器中的路由、API 前缀、Map / 私有文件和缺失资源检查 |
| deploy/check-platform.mjs | 独立生产容器测试，包含全新迁移、Secure Cookie 登录和 Map 定位 |

HTTPS 使用 Caddy，替代此前计划中的 Nginx。两个域名正确解析到香港服务器，80/443 对外可达，证书存储卷可写并持久化时，Caddy 自动申请和续期证书。[Caddy 官方说明](https://caddyserver.com/docs/automatic-https)

MySQL / Java 不映射公网端口，MySQL 所在 Docker 网络为 internal。仅 web 发布 80/443；8081 是容器内部健康检查端口，不映射宿主机。生产不加载 dev 初始化器，不会自动生成 Demo appKey 和开发账号。

## 3. 首次服务器准备

确认两个 A 记录均已替换为香港服务器公网 IP；没有可用 IPv6 时删除旧 AAAA。云安全组允许 80/443，22 只允许必要来源，不开放 3306 / 3307 / 18080。不要照搬上海服务器的腾讯云内网 mirror 配置。

在服务器当前 SSH 会话执行：

```bash
sudo apt update
sudo apt install -y jq curl openssl nano
sudo adduser --disabled-password --gecos '' traceflow-deploy
sudo usermod -aG docker traceflow-deploy
sudo install -d -m 0700 -o traceflow-deploy -g traceflow-deploy /opt/traceflow
sudo install -d -m 0700 -o traceflow-deploy -g traceflow-deploy /opt/traceflow/releases /opt/traceflow/backups
sudo install -d -m 0755 -o traceflow-deploy -g traceflow-deploy /opt/traceflow/demo
```

如果用户已存在，跳过 adduser，不重复创建。docker 组具有接近 root 的权限，这是本轮单机自动化的明确权限边界，不应把它描述为普通低权限账号。[Docker 权限说明](https://docs.docker.com/engine/install/linux-postinstall/)

服务器不需要 Node / Maven / JDK；GitHub runner 负责构建，服务器只运行镜像。2GB 是首轮限制，不是稳定支持任意采集量的承诺。当前使用 Java 768 MiB（堆 384 MiB）、MySQL 600 MiB、web 128 MiB，并限制连接和线程；上线后必须实测 OOM、磁盘和日志容量。

## 4. SSH 自动发布密钥

在本地 PowerShell 执行，生成一把只用于发布的密钥：

```powershell
ssh-keygen -t ed25519 -C 'traceflow-production' -f "$HOME\.ssh\traceflow-production"
Get-Content "$HOME\.ssh\traceflow-production.pub"
```

当前工作流不支持交互输入私钥口令，生成这把专用自动化密钥时口令留空；不要复用个人日常 SSH 私钥。私钥只放本机受限文件和 GitHub Environment Secret，不发到聊天、不提交仓库。

在服务器创建 authorized_keys，然后粘贴刚才的公钥一整行：

```bash
sudo install -d -m 0700 -o traceflow-deploy -g traceflow-deploy /home/traceflow-deploy/.ssh
sudo nano /home/traceflow-deploy/.ssh/authorized_keys
sudo chown traceflow-deploy:traceflow-deploy /home/traceflow-deploy/.ssh/authorized_keys
sudo chmod 600 /home/traceflow-deploy/.ssh/authorized_keys
```

本地验证新用户能登录并访问 Docker（替换实际 IP，SSH 非 22 时增加 -p）：

```powershell
ssh -i "$HOME\.ssh\traceflow-production" traceflow-deploy@服务器公网IP
```

登录后执行 docker version 和 docker compose version，应无需 sudo。若云镜像有额外 SSH 用户限制，先诊断登录失败，不直接修改全局 SSH 安全配置。

known_hosts 从本地 ssh-keyscan 收集，但必须通过服务器可信 SSH 会话核对指纹：

```powershell
ssh-keyscan -t ed25519 -p 22 服务器公网IP
```

服务器可信会话中的指纹：

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

核对匹配后才把 keyscan 输出填入 SSH_KNOWN_HOSTS；非 22 端口保留 [host]:port 形式。不能用 StrictHostKeyChecking=no 替代核对。

## 5. 服务器生产环境文件

模板在本地 deploy/.env.production.example。以 traceflow-deploy 登录，在服务器创建 /opt/traceflow/.env.production，并按模板填写：

```bash
umask 077
nano /opt/traceflow/.env.production
chmod 600 /opt/traceflow/.env.production
```

- APM_HOST / DEMO_HOST 只填域名，不带 https:// 或路径。
- ACME_EMAIL 填真实可收信邮箱。
- 数据库密码和 root 密码分别生成，使用 openssl rand -hex 24，得到不同的 48 位随机十六进制值。
- 初始管理员邮箱自定，密码另生成，至少 16 个字符，不用开发环境密码。
- 模板里的 CHANGE_ME 必须全部替换。不要把真实文件复制进 Git 仓库或发送到聊天。

第一次发布创建生产管理员后，删除文件中的 TRACEFLOW_BOOTSTRAP_ADMIN_EMAIL / PASSWORD 两行。下一次更新会把这两个变量清空；如要立即从容器环境移除，需要重新创建 server，现有管理员不会被删除。原数据库存在时修改 MYSQL_PASSWORD 环境变量不会自动改数据库账号密码，密码轮换需另行操作。

## 6. GitHub 配置

仓库 Settings → Environments 创建 production。在该 Environment 添加以下 Secrets：

| Secret | 内容 |
| --- | --- |
| SSH_HOST | 香港服务器公网 IP 或可解析的服务器主机名 |
| SSH_PORT | 实际 SSH 端口，通常 22 |
| SSH_USER | traceflow-deploy |
| SSH_PRIVATE_KEY | 本地专用私钥文件完整内容，不是 .pub |
| SSH_KNOWN_HOSTS | 已核对指纹的 keyscan 完整输出 |

GITHUB_TOKEN 由 GitHub 自动提供，不要手工创建同名 Secret。构建 job 用 packages:write 推送镜像；部署 job 用 packages:read 临时拉取自己的 GHCR 包。新包应关联当前仓库并允许 Actions 访问，既有包若权限不同，需要在包设置中核实，不假定私有包可以匿名拉取。

限制 production Environment 只允许 main。仓库权限 / 套餐支持时可以增加 required reviewers；即使未开启审批，workflow_dispatch 本身仍要求手动触发，不会 push 自动上线。workflow 中的串行锁和服务器 flock 还会防止发布步骤重叠。

云安全组如只允许固定 SSH 来源，GitHub 托管 runner 的地址不固定，需要选定可靠访问方案后再开放 CD；不要为了自动化顺手把数据库端口对所有 IP 开放。

## 7. 提交、CI 与发布

完成配置后再提交 / 推送本轮代码。当前还有未提交的 M4 文件，不要漏掉需要的源码、脚本和 V7 迁移；不能只推工作流却缺实现。

1. 在 GitHub Actions 等待目标 commit 的 CI 完成，包括新增的 Production image and gateway checks。
2. 打开 Deploy platform → Run workflow，选择 main，填入完整 40 位小写 commit SHA。
3. 流程确认该 commit 在 main 历史中，且对应的最新 push CI 成功；提交不存在、CI 失败 / 未完成、其他分支都会停止。
4. runner 构建两张 amd64 镜像并推送 GHCR，服务器按 digest 拉取；不同重试使用不同发布目录。
5. 服务器校验环境文件、镜像 revision；已有数据库时先流式备份，再启动候选版本并执行 Flyway 前向迁移。
6. 等待容器健康，检查公网 HTTPS API、/login 和 version.json 中的 commit 一致，才写入 SUCCESS 标记及 releases/current。

更新会重启单副本 Java / web，允许短暂维护窗口，不承诺零停机。发布前备份不是隔离迁移：仍需审查迁移兼容性。

## 8. 首次上线验收

在服务器以部署用户执行：

```bash
cd /opt/traceflow
docker compose --project-name traceflow-prod --env-file .env.production --env-file releases/current/images.env -f releases/current/compose.production.yml ps
curl --fail https://apm.revengedog.online/api/v1/health
curl --fail https://apm.revengedog.online/version.json
docker stats --no-stream
```

浏览器登录生产 Console，使用自己设置的管理员账号，不是 local@traceflow.dev。刷新 /users 等路由不应出现 404；登录 Cookie 应有 Secure / HttpOnly，未登录管理接口应拒绝请求。

第一次没有监控应用是正常的，不应照搬本地 appId=1。Demo 域名暂时返回 404 也是本轮预期，因为还没发布公共文件。下一步先创建生产 Demo 应用，allowedOrigins 为 https://demo.revengedog.online，再接 Demo 的构建 / 上传 / 公共资源发布工作流。

## 9. 发布失败、备份和回退

部署脚本失败不会自动清理数据库或尝试恢复旧 schema，候选容器可能已启动；FAILED 标记表示未通过验收，current 仅表示最后成功的发布，不保证失败后实际容器仍在运行旧版本。

从 Actions 日志确认本轮发布目录，然后用该目录的 images.env / compose.production.yml 查看 ps 和 logs。不要执行 down -v。并发更新期间不要手动改环境文件。

备份为 /opt/traceflow/backups/<发布目录名>.sql.gz，目录权限 700、文件受 umask 077 限制，包含 source_maps BLOB。失败的 .partial 不应视为有效备份。备份在同服务器，只能作为首轮更新保护，后续需独立存储、轮转和真实恢复测试；第一次空数据库没有历史备份。

需要应用回退时先确认旧代码兼容当前 schema，再用旧发布目录的两份配置手动 compose up -d --wait。镜像回退不等于数据库回退；本轮没有一键回滚按钮。数据库有破坏性迁移时停止操作，按单独恢复方案处理。

MySQL 镜像固定为当前已验证的官方 8.4 digest，普通发布不会隐式跟随可变标签升级数据库；修改 digest 前需审查 release notes、兼容性和备份，单独计划数据库版本升级。公共资源旧 hash 文件保留策略和 Demo 原子切换将在下一阶段实现。
