# V7 版本与 Source Map 表

迁移文件：`server/src/main/resources/db/migration/V7__add_releases_and_source_maps.sql`。

## 变更范围

- 新增 `releases`：应用版本、不可变 manifest、创建人、草稿 / 封存状态和时间。
- 新增 `source_maps`：未来上传的 Map 内容及 JS 路径、摘要、大小和源码覆盖数量。
- 不修改 `events`、`issues`、性能聚合表和已有用户数据。
- M4.1 首轮只建结构；后续 M4.2 已使用此表实现上传和封存，不增加 V8。堆栈还原仍留在 M4.3。
- 所有时间使用 BIGINT Unix 毫秒时间戳，未发生的封存 / 部署时间为 NULL。

## 关键约束

`releases` 的 `(application_id, release_name)` 唯一，release_name 使用 `utf8mb4_0900_bin`。`Demo@1` 与 `demo@1` 是不同版本，同一名称可在不同应用使用。应用内名称不可覆盖，重复创建时由服务层比较 canonical manifest 和 commit 决定幂等返回或 409。

manifest 为 1 到 100 项 JSON 数组。资源路径在服务层规范化、去重和排序；数据库 CHECK 仅校验外层数组大小，不能代替服务端逐条校验。

`source_maps` 的 `(release_id, artifact_path_hash)` 唯一，hash 用于规避 utf8mb4 长路径索引字节上限。后续上传实现命中 hash 时还必须比较完整路径。Map 内容用 MEDIUMBLOB 保存原始 UTF-8 字节，map_bytes 必须等于实际字节长度，源码内容数量不能超过源文件数量。

应用删除级联清理版本和 Map；创建人 / 上传人外键为 RESTRICT。M4.1 不新增删除应用或删除版本接口。

## 执行与检查

后端启动时 Flyway 自动执行，不需要重启 MySQL，也不要手动重复执行 SQL。已运行的旧后端不会自动加载新 Controller，需要重启后端进程才能使用新接口。

执行前按环境要求备份数据库。MySQL DDL 不是完整事务回滚：如果中途执行失败，先检查 Flyway 历史和两张表，修复实际失败原因后再决定恢复或 repair，不直接删库，也不直接修改已成功执行的迁移。

```sql
SELECT version, description, success
FROM flyway_schema_history
ORDER BY installed_rank DESC;

SHOW CREATE TABLE releases;
SHOW CREATE TABLE source_maps;
```

可执行真实 MySQL 集成测试：

```powershell
cd 'C:\TraceFlow APM\server'
$env:TRACEFLOW_RUN_DB_TESTS = 'true'
.\mvnw.cmd '-Dtest=ReleaseDatabaseTests' test
Remove-Item Env:TRACEFLOW_RUN_DB_TESTS
```

测试连接既有配置指定的 MySQL，启动时应用 Flyway 迁移；测试创建的用户、应用和版本通过事务回滚，不删除业务数据。执行期间关闭测试进程的性能聚合任务。建议在测试库运行，迁移本身不会随测试事务回滚。

普通 Maven test 默认跳过这组需数据库的测试，CI 的 MySQL 服务任务显式启用。测试覆盖幂等、大小写、跨应用、冲突、稳定分页、CHECK 和外键 / 唯一键。
