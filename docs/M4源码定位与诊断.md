# M4.3 源码定位与诊断

## 1. 当前结果

已实现事件级 JavaScript 堆栈还原：错误详情支持源码 / 原始堆栈切换、逐帧展开、原始位置与源码位置对照、报错行高亮、代码片段和诊断原因。

完整链路为：同一次生产构建 -> Map 私有上传 -> 版本封存 -> 真实错误上报 -> 独立定位查询 -> Console 展示。既有开发事件未上传匹配版本时仍会显示未还原，不能凭一个其他版本的 Map 自动补出位置。

本阶段没有新数据库迁移。继续读取 V7 版本和 Map，不写定位结果表，不修改事件 payload、Issue 指纹或事件数量。

## 2. 查询接口

```http
GET /api/v1/events/{eventId}/stacktrace?applicationId=1
```

- eventId 是事件数据库数字 ID，不是 SDK eventId UUID。
- 未登录返回 401；当前应用没有该事件返回 404。
- 成员与管理员都可以读取同一共享团队中的诊断内容，目前不是多租户应用成员授权。
- 响应头 `Cache-Control: private, no-store`，不允许浏览器 / 公共代理持久缓存源码响应。
- 普通诊断失败返回 200 与逐帧原因；解析并发满返回 429，原始事件接口不因此被改写。
- 原始事件详情接口保持兼容，定位通过独立请求完成，不阻塞采集写入。

顶层响应包含 eventId、releaseName、可空 releaseId、status、parserVersion、frames、diagnostics、truncated。

| status | 含义 |
| --- | --- |
| resolved | 所有处理帧均有源码坐标，且没有截断 |
| partial | 一部分帧还原成功，其他帧失败或处理范围受限 |
| unresolved | 没有成功还原的帧 |
| not_applicable | 非 error 事件或资源加载类错误，不作为 JS 堆栈定位 |

每帧保留 index、raw、generated 和独立失败原因；成功时增加 original 坐标、context、contextReason。无 sourcesContent 不等于定位失败：坐标仍可成功，代码片段为空并明确说明。

## 3. 匹配与解析规则

1. 从应用范围内读取事件及原始 error payload。
2. 解析 Chromium `at function (URL:line:column)` 或 `at URL:line:column`，保留帧顺序。
3. stack 没有可定位帧时，尝试 filename / lineno / colno。
4. 精确查找 `(applicationId, releaseName)`，只有 finalized 版本可用于定位。
5. 使用 URI 解析脚本 URL，按完整 pathname 匹配，不包含域名、query 或 fragment。
6. 使用与上传端相同的 ArtifactPath 规范化规则，拒绝穿越、编码分隔符等非法路径。
7. 验证产物路径、JS / Map 摘要、Map 字节数与存储内容的 SHA-256，再解析对应 Map。
8. 从 Map 的 sourcesContent 提取前后各 3 行，不访问服务器文件、网站 URL 或 Git 仓库。

不按 basename 匹配，不跨应用或跨版本兜底，不自动抓取 Source Map。一个第三方脚本缺 Map，不影响同一事件其他已匹配帧。

首轮不支持 Firefox `function@URL`、eval / blob / data / file URL 或 native 帧。这些保留原文并诊断，不从不支持的字符串中猜一个地址。

## 4. 行列基准与准确性

- Chromium 原始行列、API 输出和 Console 显示均采用 1-based。
- Java Closure consumer 输入 / 输出也采用 1-based，不能机械地把列号再减 1。
- 独立验证使用 `@jridgewell/trace-mapping`：传入生成行不变、生成列减 1；其原始列输出加 1后再与 Java 比较。
- 列位置遵循 UTF-16 代码单元；测试覆盖 emoji 等字符，不把 UTF-8 字节数当成字符列号。
- 缺列号或列为 0 不会被擅自改成 1。
- 库对空生成行或该行首段之前的位置可能返回前一行的近似映射。服务端只接受 Precision.EXACT，同一行没有映射时返回 NO_MAPPING。[Closure 官方实现](https://github.com/google/closure-compiler/blob/v20240317/src/com/google/debugging/sourcemap/SourceMapConsumerV3.java)
- EXACT 指 consumer 的同一生成行映射语义，不是“源码每个字符都一一对应”。Source Map 是分段映射，原始坐标可能指向相关表达式起点。
- Map 中的 names 表示符号，不一定完整描述函数定义。当前有映射名称时展示该符号，没有时保留浏览器函数名，不声称能恢复任意混淆插件抹除的函数语义。

真实生产测试直接由浏览器触发 Demo `captureManualError`，验证还原到 App.tsx 的实际 captureException 行，再独立比较列号。不是只断言一个 mock 的源码地址。

## 5. 代码片段与文本安全

- 每帧最多 7 行，每行最多 500 个 UTF-16 字符；截断处避免割断完整 surrogate pair。
- 对应源文件没有内容、坐标超出内容、同名源码包含不同内容时，不拼凑代码片段。
- 同名文件内容不唯一诊断为 AMBIGUOUS_SOURCE。
- sourceRoot 和 sources 只是展示标签，不作为磁盘路径或网络请求地址。
- React 以普通 JSX 文本节点显示源码，不使用 dangerouslySetInnerHTML，不执行代码。
- 端到端测试上传含 `<img ... onerror=...>` 的文本，验证只显示文字，没有生成 img 节点或执行脚本。

Map 可能含完整业务源码和敏感注释。当前管理员上传、已登录团队成员查看有限片段；需要严格的源码访问分级时，应另外实现权限策略。

## 6. 并发、缓存和容量

| 项目 | 当前上限 |
| --- | ---: |
| 单事件帧数 | 50 |
| 单事件实际解析的不同 Map | 10 |
| 同时定位计算 | 2 |
| 同一定位计算的等待时间 | 10 秒 |
| 单个定位响应 JSON | 256 KiB |
| 服务端结果缓存项数 | 500 |
| 服务端结果缓存序列化总字节 | 32 MiB |
| 结果缓存有效期 | 10 分钟 |

上传与读取 Map 解析还共享既有 validator 的并发保护。HTTP 超时不代表 CPU 工作自动中止，所以同时限制计算数量、帧数、Map 数及单 Map 大小。

按资源路径分组，在一次循环中处理一个 Map，不在请求结束前保留全部 consumer。解析结果只缓存有限坐标和片段，不缓存完整 consumer 或 sourcesContent。

结果键为 `(applicationId, eventId, releaseId, manifestDigest, parserVersion)`。同键的在途请求合并等待；结果按最近访问、容量和过期时间淘汰。序列化字节上限不是精确 Java 堆内存上限，后续仍需对真实堆占用压测。

未注册版本、草稿、缺 Map、损坏 Map 不长期缓存，补齐资料后可以重新查询。封存版本仍可缓存“不支持帧 / 无映射”等不会通过上传改变的诊断。

响应过大时先移除尾部帧的代码片段，再必要地省略尾部帧，明确标记 RESPONSE_LIMIT_EXCEEDED 和 truncated；原始 stack 始终从独立事件详情完整显示。

## 7. Console 状态管理

- `EventStacktrace` 作为独立组件，用 `['event-stacktrace', applicationId, eventId]` 查询。
- 选择其他事件时，通过 key 重新挂载面板，重置视图与展开项，不沿用上一条事件状态。
- 查询暂不可用时，仍可切换原始堆栈；重试按钮重新发定位查询。
- 版本页上传、删除或封存后，显式失效当前应用 event-stacktrace 查询，避免返回错误详情后继续使用旧的“未还原”缓存。
- CLI 是带外修改，前端不会收到自动通知；可点击重新定位或等待查询过期。
- SDK 数据采集、Issue 状态 mutation、面包屑和事件上下文仍独立工作。

默认“源码堆栈”不保证开发事件都会还原。诊断“尚未注册此版本”时，检查 SDK release、上传 release 和部署产物是否来自同一次构建。注册后还需要完整上传和封存。

## 8. 主要诊断

| code | 操作建议 |
| --- | --- |
| MISSING_RELEASE | 在 SDK 初始化中设置对应构建版本 |
| RELEASE_NOT_FOUND | 为当前应用创建该版本，核对大小写 |
| RELEASE_NOT_FINALIZED | 上传全部清单产物后封存 |
| SOURCE_MAP_NOT_FOUND | 核对完整 URL pathname、部署 base 和清单，不只看文件名 |
| SOURCE_MAP_UNAVAILABLE | 检查 Map 存储完整性和备份，不使用不匹配内容 |
| MISSING_POSITION | 查看原始事件的文件 / 行列信息，确认浏览器能获取堆栈 |
| UNSUPPORTED_FRAME | 首轮支持范围之外，保留原文排查 |
| NO_MAPPING | 该生成位置没有同一行映射，不自动套用前一行 |
| SOURCE_CONTENT_MISSING | 坐标可用，但构建没有携带相应源码内容 |
| SOURCE_POSITION_OUT_OF_RANGE / AMBIGUOUS_SOURCE | 构建配对或源码内容存在歧义，不能展示可信片段 |
| FRAME_LIMIT_EXCEEDED / MAP_LIMIT_EXCEEDED / RESPONSE_LIMIT_EXCEEDED | 查询达到容量边界，结合原始堆栈排查 |

系统只能报告能验证的失败原因。一个格式正确但实际配错的 Map 有时仍能返回合理坐标；摘要不能代替同一次构建流程和真实定位验收。

## 9. 验收与剩余工作

已覆盖：

- 真实 Vite 生产构建到源码位置及代码片段。
- 独立 JS consumer 的行列比对。
- 空生成行、unmapped segment、UTF-16 列、缺内容和多帧部分成功。
- 缺版本到注册、上传、封存后的后补闭环。
- 按应用查事件、私有响应缓存头和成员读取权限。
- Map 完整性失败不污染缓存、LRU / TTL / 字节容量、同请求合并。
- 源码文本 XSS 安全、切换事件、原始视图和桌面 / 移动端截图。
- 定位前后原始事件、Issue fingerprint、eventCount 保持不变。
- 用户管理、M2 错误诊断和 M3 性能闭环回归。

生产测试在 `test-results` 下保存截图与 `source-stack-example.json`，其中有本轮样例应用 / 事件 ID 和一次缓存未命中 / 命中请求耗时。这是本机单次观测，不是 P95、吞吐量或生产性能承诺。

M4.4 已补首次部署时间登记，源码定位仍只依赖封存和产物完整性，不把部署登记作为读取前提。正式验收记录与可重复演示见 [M4验收与演示](M4验收与演示.md)。远程 CI 是否通过需要提交后实际检查，不能把本地测试通过当成 GitHub Actions 已通过。
