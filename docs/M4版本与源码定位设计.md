# TraceFlow M4 版本与源码定位设计

> 设计日期：2026-10-11。本文是待实现方案，不代表功能已上线。本轮只新增设计文档，不修改业务代码、不执行数据库迁移。

后续实施进度：M4.1 已实现版本创建、列表和详情，V7 新增两张表；M4.2 已实现成对上传、草稿产物删除、封存、构建上传脚本与公共目录生成；M4.3 已实现逐帧定位、代码上下文、诊断和有界缓存；M4.4 已补首次部署登记、生产闭环回归和演示说明，远程 CI 仍须提交后验证。上述引用说明记录最初设计轮的边界。实际操作见《M4构建产物上传与发布》《M4源码定位与诊断》和《M4验收与演示》。

## 1. 目标与现状

M4 要解决：生产错误堆栈只显示压缩 JS 的位置，无法直接定位原始 React、Vue 或 TypeScript 源码。

目标链路：

```text
同一次生产构建生成 JS 和 Source Map
  -> 创建应用版本，上传每个 JS 对应的 Map
  -> 封存版本，发布不含 Map 的公共静态产物
  -> SDK 上报 release 和原始错误堆栈
  -> 服务端按应用、版本、资源路径查找 Map
  -> Console 展示原始位置、源码位置和代码片段
```

当前代码已具备：

- v1 事件有可选 `release`，后端保存为 `events.release_name`，最长 100 个字符。
- error payload 有 `stack`、`filename`、`lineno`、`colno`，无需更改协议版本。
- `GET /api/v1/events/{eventId}?applicationId=...` 返回原始 payload。
- Issue 详情已能选择事件、展示堆栈和面包屑。
- 登录采用 Session + Cookie，管理员与成员角色已实现。
- Flyway 已有 V1 到 V6，但还没有 `releases` 或 `source_maps` 表。
- Demo 的 release 目前固定为 `demo-web@0.1.0`，尚未与生产构建版本绑定。

M4 不改变事件接收是否成功，不重写历史事件，不根据还原结果重新聚合 Issue。

## 2. 范围与技术选择

### 2.1 本阶段实现

- 应用级版本列表、版本详情、创建版本和封存版本。
- 与版本绑定的 JS / Source Map 成对上传、校验、幂等重试和草稿产物删除。
- 构建上传脚本，复用现有管理员登录与 CSRF 机制。
- 服务端解析 Source Map v3，首轮覆盖 Chrome / Edge 常见 JavaScript 堆栈。
- 错误详情中的逐帧还原、原始堆栈切换和源码片段。
- 使用真实生产构建验证 Demo -> 接收 -> 查询 -> 定位闭环。

### 2.2 暂不实现

- 多组织、应用成员权限或独立 CI API Token。
- 自动抓取网站 JS、远程 Map 或 Git 仓库源码。
- indexed map 的 `sections`、远程 section URL、内联 data URL Map。
- 多阶段 Map 在服务端串联；构建工具必须提供最终 JS 到源码的完整 Map。
- CSS、WebAssembly、原生端错误还原。
- 全浏览器堆栈语法、eval 动态代码定位。
- 按还原后的源码重新计算指纹、迁移历史 Issue。
- Release 对比、独立部署历史、回滚编排、回放与告警。
- Redis、对象存储、任务队列或新增 Node 服务。

### 2.3 解析和存储

解析在现有 Java 后端完成，优先通过 Google Closure 的 `SourceMapConsumerV3` 适配，不手写 VLQ 解码器。只使用 Source Map consumer，不用它重新编译业务 JS。[官方实现](https://github.com/google/closure-compiler/blob/master/src/com/google/debugging/sourcemap/SourceMapConsumerV3.java)

实现前做一个小型兼容性验证：真实 Vite 6 构建 Map、已知原始坐标、源码内容读取、解析边界和 Java 17 字节码兼容性。依赖版本验证后固定在 POM，不直接追随最新版；运行机器安装 JDK 25，不等于项目可以引入要求更高字节码版本的依赖。

首轮 Map 的 UTF-8 原始字节存入 MySQL `MEDIUMBLOB`。原因是单团队、低频上传，现有备份和容器数据持久化可以一起覆盖，不增加文件系统与数据库一致性问题。列表查询严禁读取大字段；后续数据量增大时迁移到私有对象存储，不对外承诺无限容量。

## 3. 版本身份与生命周期

### 3.1 匹配键

版本唯一身份是 `(applicationId, releaseName)`，不是 releaseName 单独唯一。

- 名称最长 100 个字符，拒绝空白、首尾空格与控制字符。
- 大小写敏感，不做隐式小写或 trim 后匹配。
- 数据库存储使用显式区分大小写的排序规则，避免默认 MySQL 排序规则合并两个名称。
- 事件 release 必须与构建内嵌的 release、上传版本名称完全一致。
- 建议名称为 `demo-web@0.2.0+<短commit>-<buildId>`；commit 是追踪信息，不独自代表构建产物。
- 同一个 commit 可能因依赖、环境变量或构建参数不同产生不同产物；不同构建必须使用不同版本身份。
- 已注册名称不可改名或复用。回滚同一批产物可复用原版本，但不覆盖其 Map。

`environment` 不参与 Map 身份。相同构建部署到多个环境可以共用版本；如果把环境变量编译进 JS 导致字节变化，必须换版本。M4 的 `deployedAt` 仅为首次部署记录，不冒充多环境部署历史。

### 3.2 状态

| 状态 | 含义 | 可执行操作 |
| --- | --- | --- |
| `draft` | 正在上传和校验产物 | 上传、删除草稿产物、封存 |
| `finalized` | 产物集合已封存 | 查询、还原、登记首次部署时间 |

封存不是部署完成。`finalizedAt` 与 `deployedAt` 分开表示。

首次部署登记要求版本已经封存，使用毫秒时间戳且不早于 `finalizedAt`，至多允许服务器当前时间之后一分钟以容忍轻微时钟偏差。登记和封存共用版本行锁；同一时间重试幂等，不同时间冲突。管理员页面按浏览器本地时间选择并转换为时间戳。登记只是记录人工确认的发布事实，不自动发布网站，也不提供多环境历史。

- 创建时声明预期 JS 路径及 JS、Map 的 SHA-256，形成不可变 manifest。
- 只有全部 manifest 项目上传且校验成功，才能封存。
- 草稿不能用于生产还原，避免上传中途提供不完整定位结果。
- 封存后允许完全相同的幂等重传，不允许新增、替换或删除产物。
- 草稿中传错文件时先删除对应产物再上传；manifest 本身传错则创建新版本，不能随意改写身份。
- 已接收事件不要求版本提前存在。先到事件、后补齐产物仍可在查询时还原。

## 4. 资源路径匹配

完整身份为 `(applicationId, releaseName, artifactPath)`。

上传时的 `artifactPath` 是部署 URL 的完整 pathname，例：

```text
JS URL:       https://cdn.example.com/traceflow/assets/index-AbCd.js?v=123
artifactPath: /traceflow/assets/index-AbCd.js
```

规范：

- 用 URI 解析器提取 URL pathname，移除 query / fragment；不依赖手写字符串切割。
- 保留大小写和部署 base 前缀，不只取 basename，不跨版本找“最像”的文件。
- 域名不参与身份，同一版本的不同域名必须服务相同路径下的相同 JS 字节；否则该部署不受首轮方案支持。
- 路径必须以 `/` 开头，最长 1024 个字符。
- 统一百分号编码表示并且只做一次受控规范化；不把编码后的 `/`、`\\` 当作分隔符。
- 拒绝控制字符、反斜杠、路径穿越片段、编码后的穿越或分隔符、无效百分号编码。
- 首轮只支持 HTTP(S) 脚本 URL；blob、data、eval、native 等帧保留原文，不猜位置。
- 上传端和解析端共享相同的路径规范化测试用例。

同名文件示例：`/a/index.js` 和 `/b/index.js` 必须是两个独立产物。

## 5. 构建与上传流程

### 5.1 构建约定

未来 Demo 生产构建配置采用 `build.sourcemap: 'hidden'`，并从构建环境读取 release，传给 SDK。

Vite 的 hidden Map 仍会生成 `.map` 文件，只是不在 JS 末尾添加引用注释。因此 hidden 不是访问权限控制，公共发布目录必须显式排除 Map。[Vite 官方说明](https://vite.dev/config/build-options)

顺序必须是：确定 release -> 构建一次 -> 上传这一批 Map -> 封存 -> 从同一批产物生成公共发布目录。上传后再次构建，会破坏同一次构建的对应关系。

输出分为：

- 私有构建目录：包含 JS 与 Map，用于上传。
- 公共发布目录：包含 HTML、JS、CSS 等，不含 `.map`、manifest 中的源码内容或其他私有文件。

所有后续转换（压缩、混淆、插件加工）都必须正确组合 Map；不能在生成 Map 后再无映射地修改 JS。M4 不保证任意第三方混淆插件都可还原。

### 5.2 上传脚本

建议后续新增 `scripts/upload-source-maps.mjs`，不建立新的 npm workspace。脚本使用 Node 标准文件、路径、crypto 和 fetch API。

输入配置：

| 参数 / 环境变量 | 含义 |
| --- | --- |
| `--application-id` | 应用 ID |
| `--release` | 与 SDK 完全一致的版本名 |
| `--dist` | 私有构建目录 |
| `--url-prefix` | 部署 pathname 前缀，例如 `/traceflow/` |
| `--commit` | 可选 commit SHA |
| `TRACEFLOW_API_BASE` | API 根地址 |
| `TRACEFLOW_UPLOAD_EMAIL` | 管理员邮箱 |
| `TRACEFLOW_UPLOAD_PASSWORD` | 管理员密码，只从环境读取，不放命令参数 |

脚本扫描 dist 中 `.js.map` 与对应 `.js`，每个 lazy chunk 都要包含在 manifest。遇到缺 JS、缺 Map、符号链接指向目录外、空产物集合或重复路径立即失败，不静默跳过。

认证复用 Session：获取 CSRF -> 登录 -> 保存 Cookie -> 获取登录后的新 CSRF -> 创建版本与逐个上传 -> 封存 -> 退出。脚本不是浏览器，不会自动保存 Cookie，需显式维护 Cookie，并处理登录后 token 轮换。

网络超时后先查询服务器已有 checksum，再决定重试；只重试网络错误和允许的临时错误，不反复重试 400 / 401 / 403 / 409。失败必须返回非零退出码，日志不打印密码、Cookie、Token 或源码。生产上传仅使用 HTTPS。

通过 appKey 可以上报事件，但 appKey 不是上传凭证。未来自动化专用 Token 可单独设计，M4 不混用采集密钥和管理权限。

### 5.3 Map 校验与边界

multipart 上传包含 `artifactPath`、`javascript` 文件、`sourceMap` 文件；首轮不接收 ZIP，避免引入解压炸弹和归档路径穿越。

- Map 必须是有效 UTF-8 JSON，`version` 为数字 3。
- 验证 `sources`、`names`、`mappings` 类型、索引、坐标和映射可解析性。
- 存在 `sourcesContent` 时，长度必须与 `sources` 一致；允许其中元素为 null。
- `file` 若存在，必须与生成 JS 的文件名一致；若不存在，使用显式 artifactPath。
- `sections` 返回明确的“不支持格式”错误，不假装成功。
- 所有 JS 和 Map checksum 都由服务端重新计算，必须与 manifest 一致。
- 同一路径相同 checksum 返回现有产物；不同 checksum 返回 409，不能静默覆盖。

checksum 能验证传输一致性和幂等性，不能独自证明某个 Map 数学上确实对应某个 JS。配对依赖受信任的同一次构建流程、产物 manifest 和真实定位测试；系统不能保证识别任意恶意上传的“错配但格式正确”的文件。

首轮默认限制（可配置，但必须设置上限）：

| 项目 | 默认上限 |
| --- | ---: |
| 单个 JS | 5 MiB |
| 单个 Map（包含源码） | 5 MiB |
| multipart 总请求 | 11 MiB |
| 单版本产物数 | 100 |
| 单版本 Map 原始字节总量 | 100 MiB |
| 单 Map sources / names | 各 20,000 |
| 单 Map 映射段数 | 500,000 |
| 单事件解析帧数 | 50 |
| 返回代码上下文 | 报错行前后各 3 行，每行最多 500 字符 |

同步解析须限制并发和排队长度，避免上传 Map 耗尽 HTTP 工作线程。JSON 深度、字符串长度和映射段数量在大对象建立前尽量受控；仅设置 HTTP 请求超时不能中止已经占用 CPU 的解析工作。

## 6. 首轮数据库迁移设计

计划新增 `V7__add_releases_and_source_maps.sql`。落地前再确认迁移编号未被其他工作使用，不修改已执行 V1-V6。

### 6.1 releases

| 字段 | 类型 | 约束 / 含义 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | 自增主键 |
| application_id | BIGINT UNSIGNED | FK applications，ON DELETE CASCADE |
| release_name | VARCHAR(100) | NOT NULL，区分大小写 |
| commit_sha | VARCHAR(64) | 可空，验证十六进制 SHA 格式 |
| status | VARCHAR(20) | draft / finalized |
| manifest | JSON | 不可变产物路径、JS / Map SHA-256 列表 |
| artifact_count | INT UNSIGNED | 已成功上传数量，默认 0 |
| total_map_bytes | BIGINT UNSIGNED | 已上传 Map 字节数，默认 0 |
| created_by | BIGINT UNSIGNED | FK users，ON DELETE RESTRICT |
| created_at | BIGINT | Unix 毫秒时间戳 |
| finalized_at | BIGINT | 可空，封存时间 |
| deployed_at | BIGINT | 可空，首次部署时间 |

唯一键 `(application_id, release_name)`；列表索引 `(application_id, created_at DESC, id DESC)`。状态和非负时间设置 CHECK；查询排序始终以 id 作为同时间下的稳定次序。

### 6.2 source_maps

| 字段 | 类型 | 约束 / 含义 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | 自增主键 |
| release_id | BIGINT UNSIGNED | FK releases，ON DELETE CASCADE |
| artifact_path | VARCHAR(1024) | 规范化后的完整 JS pathname |
| artifact_path_hash | CHAR(64) ASCII | 服务端对规范化路径计算 SHA-256 |
| js_sha256 | CHAR(64) ASCII | JS 原始字节摘要 |
| map_sha256 | CHAR(64) ASCII | Map 原始字节摘要 |
| js_bytes | BIGINT UNSIGNED | JS 上传大小，仅保留元数据 |
| map_bytes | BIGINT UNSIGNED | Map 原始字节大小 |
| map_content | MEDIUMBLOB | Map UTF-8 原始字节，不保存 JS 原始文件 |
| source_count | INT UNSIGNED | 源文件数量 |
| sources_with_content | INT UNSIGNED | 有源码内容的源文件数量 |
| uploaded_by | BIGINT UNSIGNED | FK users，ON DELETE RESTRICT |
| uploaded_at | BIGINT | Unix 毫秒时间戳 |

唯一键 `(release_id, artifact_path_hash)`，避免 utf8mb4 长路径复合索引超过字节限制。查询或写入命中 hash 后必须同时比较完整路径，发生 hash 冲突返回显式错误，不错误复用另一个文件。

只保存校验成功的产物，不持久化“上传中”或失败大文件。失败原因由接口返回；本阶段不建立上传任务表。

上传事务先锁定所属 release 行，再校验状态、唯一性、数量和总量，插入 Map 并更新计数；封存和删除也锁同一行。这样并发上传不会绕过版本配额或与封存交错。大文件解析在事务外完成，事务内只做最后一致性检查与写入。

删除草稿产物同步扣减计数与大小。幂等上传不重复累加。相同名称创建时比较不可变 manifest / commit，相同则复用，不同则返回 409。

### 6.3 为什么不改 events

`events.release_name` 已足够关联版本，不增加强制 release_id FK，不回填旧事件，也不拒绝版本尚未创建的上报。还原通过查询时关联完成，避免把构建管理变成采集可用性的依赖。

全部新时间字段使用 Unix 毫秒时间戳，服务端保存数值，Console 展示时按用户时区格式化。

Map 不随事件清理任务自动删除，避免删掉仍被其他历史事件使用的产物。首轮不提供封存版本删除；必须监控库容量，不能宣称已有自动保留策略。后续统一设计版本保留与归档，并将 Map 纳入数据库备份及恢复验收。

## 7. 管理接口

以下为待实现接口，响应风格继续沿用现有直接 DTO 与 `items/total/page/pageSize` 分页，不新增统一外壳。

M4.1 已实现前三项，M4.2 增加产物列表、上传、草稿产物删除和封存。详情与创建返回 `{ release: ReleaseSummary, artifacts: ArtifactInput[] }`，列表返回分页摘要，不携带 manifest 或 Map 内容。首次创建返回 201，完全相同的幂等创建返回 200；manifest 规范化并按路径排序后比较，顺序不同不产生冲突。

| 方法 | 地址 | 功能 | 权限 |
| --- | --- | --- | --- |
| GET | `/api/v1/releases?applicationId=...` | 分页列表，支持名称和状态筛选 | 已登录 |
| POST | `/api/v1/releases` | 创建或幂等复用草稿 | admin + CSRF |
| GET | `/api/v1/releases/{id}?applicationId=...` | 版本详情及上传完整度 | 已登录 |
| GET | `/api/v1/releases/{id}/source-maps?applicationId=...` | 产物元数据列表，不返回 map_content | 已登录 |
| POST | `/api/v1/releases/{id}/source-maps?applicationId=...` | 成对上传 JS / Map | admin + CSRF |
| DELETE | `/api/v1/releases/{id}/source-maps/{mapId}?applicationId=...` | 删除草稿产物 | admin + CSRF |
| POST | `/api/v1/releases/{id}/finalize?applicationId=...` | 校验 manifest 完整并封存 | admin + CSRF |
| PATCH | `/api/v1/releases/{id}/deployment?applicationId=...` | 登记首次部署时间；相同值幂等，不同值冲突 | admin + CSRF |
| GET | `/api/v1/events/{eventId}/stacktrace?applicationId=...` | 按需还原事件堆栈 | 已登录 |

当前系统是共享单团队，成员可读全部应用的诊断信息和有限代码上下文。这不是租户隔离。若需要限制源码访问，必须新增权限设计，不能把“已登录”描述为“仅本应用成员”。

所有包含 applicationId 的接口必须校验真实归属，不能凭 releaseId / mapId 跨应用读取。当前 eventId 是数据库数字 ID，不是事件 UUID。

创建输入示意：

```json
{
  "applicationId": 1,
  "releaseName": "demo-web@0.2.0+abc123-build1",
  "commitSha": "0123456789abcdef0123456789abcdef01234567",
  "artifacts": [
    {
      "artifactPath": "/assets/index-AbCd.js",
      "jsSha256": "<64位小写十六进制>",
      "mapSha256": "<64位小写十六进制>"
    }
  ]
}
```

示例中的占位摘要不是有效请求值。manifest 最多 100 项，不允许空集合或重复路径。

关键失败语义：

| HTTP | code 示例 | 场景 |
| --- | --- | --- |
| 400 | INVALID_RELEASE / INVALID_ARTIFACT_PATH / INVALID_SOURCE_MAP | 输入或 Map 无效 |
| 400 | UNSUPPORTED_SOURCE_MAP | 不支持的 indexed / 远程 Map |
| 401 / 403 | 沿用认证错误 | 未登录、会话失效、非管理员、缺少 CSRF |
| 404 | APPLICATION_NOT_FOUND / RELEASE_NOT_FOUND / EVENT_NOT_FOUND | 资源不存在或归属不匹配 |
| 409 | RELEASE_CONFLICT / ARTIFACT_CONFLICT / RELEASE_FINALIZED | 身份或产物不一致、封存后修改 |
| 409 | RELEASE_INCOMPLETE / RELEASE_QUOTA_EXCEEDED | 不能封存或总量超额 |
| 413 | UPLOAD_TOO_LARGE | multipart 或单文件超限 |
| 429 | SOURCE_MAP_BUSY | 校验 / 解析并发容量已满 |

上传失败不改变已有有效产物；错误信息不包含服务端路径和源码。解析结果中的“缺 Map”属于正常诊断状态，不应让错误详情整个返回 500。

## 8. 堆栈还原

### 8.1 按需查询，不阻塞上报

事件详情 API 保持原样；新增 stacktrace 查询，Console 取得选中事件后再单独请求。

1. 校验用户身份及事件所属应用。
2. 如果不是可定位的 JavaScript 错误，返回 `not_applicable`。
3. 解析原始 stack 的帧，保留全部原文与顺序。
4. stack 无可解析帧时，尝试 payload.filename / lineno / colno。
5. 精确查找应用和 release，再查找每帧 artifactPath。
6. 对每一帧独立还原；一个第三方帧失败不影响其他帧。
7. 从 Map 内 sourcesContent 读取有限上下文，不读取服务器文件或网络地址。
8. 返回结果；不修改原始事件、Issue、事件数量或指纹版本。

先覆盖 Chromium 的 `at function (url:line:column)` 和 `at url:line:column`。通过末尾坐标和 URI 解析处理端口号，不简单按冒号切割。未知语法原样显示并诊断为不支持。

### 8.2 行列基准

- Console 与 API 对外统一 line / column 从 1 开始。
- 首轮 Chromium Error.stack 与 ErrorEvent 的位置按 1-based 适配；缺失或 0 不强行转成 1。
- Source Map 编码位置与 consumer API 的坐标约定不一定一致，所有转换集中在解析适配器。
- Closure `getMappingForLine` 文档约定输入行、列均从 1 开始，不应机械地再把浏览器列号减 1。[官方接口](https://github.com/google/closure-compiler/blob/master/src/com/google/debugging/sourcemap/SourceMapping.java)
- 原始输出坐标以真实 fixtures 验证，必须覆盖第一行第一列、多行代码、非 ASCII 字符和 unmapped segment。
- 映射通常定位到相邻代码段，不保证还原到抛错表达式中的每个字符。函数名缺失时保留浏览器给出的名称，不凭空生成。

### 8.3 响应结构

```ts
interface StacktraceResponse {
  eventId: number
  releaseName: string | null
  status: 'resolved' | 'partial' | 'unresolved' | 'not_applicable'
  parserVersion: number
  frames: Array<{
    index: number
    raw: string
    status: 'resolved' | 'unresolved'
    reason: string | null
    generated: {
      functionName: string | null
      filename: string | null
      line: number | null
      column: number | null
    }
    original: {
      functionName: string | null
      filename: string
      line: number
      column: number
      context: Array<{ line: number; content: string; isErrorLine: boolean }>
      contextReason: string | null
    } | null
  }>
  diagnostics: Array<{ code: string; message: string }>
  truncated: boolean
}
```

响应不返回完整 Map、完整 sourcesContent、登录凭证或内部存储地址。原始 stack 仍从事件详情取得；超过 50 帧明确标记截断，不能误报全部还原。

诊断码包括：MISSING_RELEASE、RELEASE_NOT_FOUND、RELEASE_NOT_FINALIZED、SOURCE_MAP_NOT_FOUND、UNSUPPORTED_FRAME、MISSING_POSITION、NO_MAPPING、SOURCE_CONTENT_MISSING、FRAME_LIMIT_EXCEEDED、SOURCE_MAP_UNAVAILABLE。

没有 sourcesContent 仍可以成功还原坐标，`context` 为空并设置 contextReason，不把它计为定位失败。resolved 表示纳入处理的帧全部已映射且无未处理帧；有成功帧也有失败帧为 partial，没有成功帧为 unresolved。解析器不靠猜测判断“业务代码”，默认将可解析 HTTP(S) JS 帧纳入统计，第三方帧可单独标注但不丢弃。

未注册 release 与 missing Map 只能说明无法找到对应资料，不能准确断言“版本上传错了”。错配 Map 有时仍会返回看似有效的坐标，必须在 UI 和文档中明确定位结果依赖正确构建配对。

### 8.4 缓存与资源消耗

使用单进程有界缓存，不新增缓存结果表。解析结果键至少包含 `(applicationId, eventId, releaseId, manifestDigest, parserVersion)`；只缓存封存版本，缺版本 / 草稿 / 缺 Map 的负结果不长期缓存，补传后可以重新查询成功。

首轮不缓存无限量的 Map consumer。结果缓存限制最多 500 项、最长 10 分钟，同时按序列化响应字节设置 32 MiB 总容量上限；单响应最多 256 KiB，代码片段超额时优先截断并标记。实际 Java 对象堆占用需额外测量，不能将序列化大小当作精确堆大小。大 Map 解析通过有限并发控制，库对象体积不能只按文件大小估算。相同请求可合并在途计算。缓存变化不产生 DB 写操作。

页面刷新按钮同时 refetch 当前事件定位查询。没有 Map、解析失败或服务繁忙时，只展示诊断与重试，不阻塞已有错误详情。

## 9. Console 页面与 React 状态

### 9.1 Release 页面

应用导航增加“版本”，路径 `/apps/:appId/releases` 与 `/apps/:appId/releases/:releaseId`。

- 列表展示名称、commit、状态、已上传 / 预期产物数、创建 / 封存 / 首次部署时间。
- 详情展示完整 artifactPath、checksum 摘要、大小、源码内容覆盖率和缺失产物。
- 管理员可创建、成对上传、删除草稿产物、封存；成员只读。
- 首轮浏览器上传一次一对 JS / Map，批量上传交给脚本；不在表单里解析或展示整个 Map。
- 采用现有 Ant Design、Tailwind 和紧凑工作台布局，不另建一套风格。

React Query keys 按资源与过滤条件划分：`['releases', appId, filters]`、`['release', appId, releaseId]`、`['source-maps', appId, releaseId]`、`['event-stacktrace', appId, eventId]`。新增上传或封存后显式 invalidate 关联查询；服务端封存后补齐 Map 的情形，页面提供手动重试。

### 9.2 错误详情

- 默认展示还原结果，提供“源码堆栈 / 原始堆栈”切换。
- 逐帧显示原始位置、还原位置、函数名和解析状态，不只展示第一帧。
- 展开帧查看有限代码上下文；文本按普通文本渲染，不能使用 dangerouslySetInnerHTML。
- release 已存在时可跳到版本详情；未注册时展示原始版本名称和明确提示。
- 选择事件变化后，以新 eventId 查询，不复用上一条事件的定位状态。
- 暂不做编辑器深链接、外部源码链接或通用代码编辑器。

实现时继续补充 React / Vue 差异注释：表单 props / callback 对应 props / emit；mutation 成功不自动同步列表，需失效缓存；ref 与普通变量的生命周期区别。只在确有学习价值处注释。

## 10. 安全与运行约束

- JS / Map 上传仅管理员可用；写接口保留 CSRF，SDK 上报豁免不扩展到管理接口。
- 不提供匿名 Map 下载接口，不把数据库 Map 转存到公共静态目录。
- stacktrace 和管理响应设置适当的私有 / no-store 缓存策略，防止代理缓存源码片段。
- sources、sourceRoot、file 均视为不可信标签，不用于本地文件访问或远程请求。
- 不自动下载 stack 中的 URL，防止 SSRF；Map 中的远程源文件也不下载。
- Map 可包含完整源码、注释甚至误写入的秘密；上传前应检查构建产物，APM 不能保证自动移除所有敏感内容。
- SQL 查询参数化；路径与名称不要直接拼 SQL。源码作为纯文本展示，覆盖 XSS 回归。
- 大文件、映射段、并发与版本配额都有边界；容量不足时明确失败，不拖垮事件采集。
- 上传产物与登录机密不提交 Git，不把生产密码写入 `.env` 示例。
- MySQL 持久卷和备份一起保护 Map，恢复测试同时检查版本元数据与 Map checksum。

## 11. 实施顺序

### M4.1 版本管理基础

### M4.2 构建产物上传

- 完成 Java consumer 的真实 Vite Map 兼容性验证并固定依赖。

### M4.3 逐帧还原与详情

- 实现 stack parser、路径匹配、行列适配与源码上下文。

### M4.4 生产闭环与关闭

- 独立登记首次部署毫秒时间戳，补权限、CSRF、时间范围、幂等和并发冲突测试。

- 更新 README、发布步骤与故障排查，记录实际构建和解析性能数据。

验收：全新环境可重复演示，同一构建的 JS / Map 配对可追溯，源码不公开，失败原因可解释。

## 12. 测试清单

| 层级 | 必测内容 |
| --- | --- |
| DB / API | 唯一键、大小写、跨应用归属、时间戳、分页、成员写入被拒绝、缺 CSRF |
| 上传 | 格式错误、sections、缺文件、超限、超额、路径穿越、checksum 错误 |
| 并发 | 同一路径重复上传、计数不重复、删除与上传、上传与封存竞争 |
| 构建 | hidden Map、所有动态 chunk、SDK release 一致、非根 base 路径 |
| 映射 | 1-based 边界、多行、UTF-16 字符、无映射段、空名称、缺源码内容 |
| 堆栈 | 端口 URL、query / fragment、多个帧、第三方帧、无 stack 的 filename fallback |
| 降级 | release 缺失、版本未注册、草稿、缺 Map、超帧数、不支持语法 |
| UI | 切换事件、原始 / 源码切换、纯文本源码、上传失败保留表单与可重试 |
| 缓存 | 先有事件后上传、封存后重试、账号切换清空前端缓存、容量淘汰 |
| 生产 E2E | 构建一次、上传封存、页面真实报错、源码片段准确、Map 公网不可访问 |

生产 E2E 不使用 Vite dev server 充当压缩代码验证。使用独立构建目录与端口，后端配置允许该 Demo origin；不能覆盖开发应用的 allowedOrigins，也不能让生产测试产生的数据污染现有 M2/M3 的断言。版本名和事件测试标记唯一，清理策略不删除已封存版本。

测试应保存已知源码定位的 fixture，通过实际浏览器堆栈与 consumer 结果验证行列，而不是只 mock 一个“看起来正确”的响应。至少覆盖 Windows 开发环境与 Linux CI。

## 13. 进入开发前的结论

1. 先从 M4.1 版本管理基础开始，不同时铺开上传、解析和 UI。
2. 新增两张表，复用 v1 release 和原始 payload，不改原始事件数据模型。
3. 版本按应用隔离，资源按完整 pathname 匹配；不做 basename 或跨版本兜底。
4. Map 对应关系依赖同一次构建，manifest 与 checksum 不能代替真实定位验收。
5. 首轮 Java 服务端解析、MySQL 私有存储、按需查询，保持基础设施简单且有明确容量边界。
6. Release 管理和源码定位失败不得破坏现有监控采集与查询链路。
