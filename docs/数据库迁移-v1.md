# TraceFlow 首轮数据库迁移设计

> 本文描述 M0/M1 使用的 MySQL 结构，并与《事件协议 v1》保持一一对应。可执行 SQL 位于服务端 Flyway migration 目录。

## 1. 迁移范围

首个迁移 `V1__create_core_tables.sql` 创建：

- `users`：管理后台用户。
- `applications`：被监控应用与接入配置。
- `issues`：错误聚合实体。
- `events`：原始 PV、错误和 HTTP 事件。

M0 暂不创建成员、Release、Source Map、告警、回放和指标桶表。它们在对应功能开始前通过新的 Flyway 版本增加，不修改已经执行的 V1。

## 2. 数据库约定

| 项目 | 约定 |
| --- | --- |
| 数据库 | MySQL 8.4 或兼容的 MySQL 8.x |
| 字符集 | `utf8mb4` |
| 排序规则 | `utf8mb4_0900_ai_ci` |
| 存储引擎 | InnoDB |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` |
| 时间精度 | `DATETIME(3)`，统一存 UTC |
| 布尔值 | `BOOLEAN`，实际映射为 `TINYINT(1)` |
| JSON | 使用原生 `JSON` 类型 |
| 命名 | 表名和列名均为 snake_case |

应用层连接必须设置 `connectionTimeZone=UTC`，前端展示时再按用户时区转换。

## 3. 表关系

```text
users 1 ---- n applications
applications 1 ---- n issues
applications 1 ---- n events
issues 1 ---- n events（仅 error 事件，其他事件为空）
```

V1 先用 `applications.created_by` 表示所有者。多人协作时再新增 `application_members`，避免首版出现只有一个用户却维护完整 RBAC 的空复杂度。

## 4. `users`

| 列 | 类型 | 空值 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint unsigned | 否 | 主键 |
| `email` | varchar(191) | 否 | 登录邮箱，统一小写 |
| `password_hash` | varchar(255) | 否 | BCrypt/Argon2 哈希 |
| `display_name` | varchar(100) | 否 | 显示名称 |
| `status` | varchar(20) | 否 | active/disabled |
| `created_at` | datetime(3) | 否 | 创建时间 |
| `updated_at` | datetime(3) | 否 | 更新时间，由应用更新 |

索引：`uk_users_email(email)` 唯一。首迁移不插入默认密码，开发管理员通过 dev profile 初始化，生产环境必须显式提供初始账号。

## 5. `applications`

| 列 | 类型 | 空值 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint unsigned | 否 | 主键 |
| `name` | varchar(100) | 否 | 应用名称 |
| `app_key` | varchar(64) | 否 | SDK 接入标识 |
| `platform` | varchar(20) | 否 | V1 固定为 web |
| `allowed_origins` | json | 否 | 字符串数组 |
| `retention_days` | int unsigned | 否 | 默认 30 |
| `status` | varchar(20) | 否 | active/disabled |
| `created_by` | bigint unsigned | 否 | 所有者用户 ID |
| `created_at` | datetime(3) | 否 | 创建时间 |
| `updated_at` | datetime(3) | 否 | 更新时间 |

索引：

- `uk_applications_app_key(app_key)`：SDK 查询应用。
- `idx_applications_owner(created_by, status)`：后台应用列表。

`app_key` 使用 `tf_app_` 前缀加不可预测随机串。它不是密钥，但不使用自增 ID，避免无意义的批量探测。

## 6. `issues`

| 列 | 类型 | 空值 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint unsigned | 否 | 主键 |
| `application_id` | bigint unsigned | 否 | 所属应用 |
| `fingerprint` | char(64) | 否 | SHA-256 十六进制摘要 |
| `title` | varchar(500) | 否 | 错误摘要 |
| `error_type` | varchar(100) | 否 | TypeError 等 |
| `status` | varchar(20) | 否 | 默认 unresolved |
| `level` | varchar(20) | 否 | V1 默认 error |
| `first_seen_at` | datetime(3) | 否 | 首次事件时间 |
| `last_seen_at` | datetime(3) | 否 | 最近事件时间 |
| `event_count` | bigint unsigned | 否 | 聚合事件总数 |
| `affected_user_count` | bigint unsigned | 否 | V1 可先近似维护 |
| `latest_event_id` | bigint unsigned | 是 | 最新事件，不建外键 |
| `created_at` | datetime(3) | 否 | 创建时间 |
| `updated_at` | datetime(3) | 否 | 更新时间 |

索引：

- `uk_issues_app_fingerprint(application_id, fingerprint)`：同应用错误聚合。
- `idx_issues_app_last_seen(application_id, last_seen_at DESC)`：默认列表。
- `idx_issues_app_status_last_seen(application_id, status, last_seen_at DESC)`：状态筛选。

`affected_user_count` 在 MVP 中允许近似值，准确去重统计在指标聚合阶段实现。并发聚合不能只依赖插入前查询，应由唯一索引和事务内 upsert 收口。

## 7. `events`

### 7.1 通用与筛选列

| 列 | 类型 | 空值 | 来源 |
| --- | --- | --- | --- |
| `id` | bigint unsigned | 否 | 服务端主键 |
| `event_id` | char(36) | 否 | 协议 eventId |
| `application_id` | bigint unsigned | 否 | appKey 解析结果 |
| `issue_id` | bigint unsigned | 是 | error 聚合结果 |
| `schema_version` | smallint unsigned | 否 | 批次 schemaVersion |
| `type` | varchar(30) | 否 | page_view/error/http |
| `occurred_at` | datetime(3) | 否 | 协议 timestamp |
| `received_at` | datetime(3) | 否 | 服务端接收时间 |
| `environment` | varchar(40) | 否 | 协议 environment |
| `release_name` | varchar(100) | 是 | 协议 release |
| `session_id` | varchar(64) | 否 | 协议 sessionId |
| `anonymous_id` | varchar(64) | 是 | 协议 anonymousId |
| `user_id` | varchar(100) | 是 | 协议 user.id |
| `trace_id` | varchar(64) | 是 | 协议 traceId |
| `page_url` | varchar(2048) | 否 | 已脱敏 page.url |
| `page_path` | varchar(1024) | 否 | page.path |

### 7.2 类型热点列

| 列 | 类型 | 适用事件 | 说明 |
| --- | --- | --- | --- |
| `error_name` | varchar(100) | error | 错误类型 |
| `error_message` | varchar(2000) | error | 错误摘要 |
| `http_method` | varchar(16) | http | 请求方法 |
| `http_url` | varchar(2048) | http | 已脱敏请求 URL |
| `http_status` | smallint unsigned | http | HTTP 状态码 |
| `http_duration_ms` | decimal(12,3) | http | 请求耗时 |
| `http_outcome` | varchar(20) | http | success/failure/aborted |

这些列避免错误列表和网络列表依赖 JSON 表达式。完整 payload 仍保留，详情页不需要把每个字段都拆成列。

### 7.3 JSON 与审计列

| 列 | 类型 | 空值 | 说明 |
| --- | --- | --- | --- |
| `payload` | json | 否 | 对应事件 payload |
| `context` | json | 否 | page、user、device、tags、sdk 等上下文 |
| `breadcrumbs` | json | 是 | 最多 50 条 |
| `created_at` | datetime(3) | 否 | 入库时间 |

### 7.4 索引

- `uk_events_app_event(application_id, event_id)`：最终幂等。
- `idx_events_app_type_occurred(application_id, type, occurred_at DESC)`：事件列表。
- `idx_events_issue_occurred(issue_id, occurred_at DESC)`：Issue 下事件。
- `idx_events_app_release_occurred(application_id, release_name, occurred_at DESC)`：版本筛选。
- `idx_events_app_user_occurred(application_id, user_id, occurred_at DESC)`：影响用户查询。
- `idx_events_app_http_status_occurred(application_id, http_status, occurred_at DESC)`：请求状态筛选。

`page_url`、`http_url` 太长，不在 V1 上建立完整 B-Tree 索引。URL 搜索先采用受限模糊查询；数据量和查询模式明确后，再增加规范化 URL、前缀索引或专用检索方案。

## 8. 外键策略

- `applications.created_by -> users.id`，删除用户时限制。
- `issues.application_id -> applications.id`，删除应用时级联。
- `events.application_id -> applications.id`，删除应用时级联。
- `events.issue_id -> issues.id`，删除 Issue 时置空。

`issues.latest_event_id` 不建立外键，避免 `issues` 与 `events` 的循环依赖。应用删除属于低频显式操作，未来数据量变大后应改为异步清理，不直接执行大事务级联。

## 9. 写入事务

非错误事件：解析 `appKey`，依靠 `(application_id, event_id)` 判断幂等，将公共字段、热点字段和 JSON 内容写入 `events`。

错误事件：

1. 归一化 message 与首个有效堆栈帧，生成 SHA-256 fingerprint。
2. 在事务中 upsert `issues`，更新次数与最近发生时间。
3. 插入 `events` 并关联 `issue_id`。
4. 回写 `issues.latest_event_id`。

若插入事件命中唯一索引，则判定重复，不增加 Issue 计数。应用代码必须依赖数据库唯一索引收口并发，而不是只依赖插入前查询。

## 10. 保留与删除

- `applications.retention_days` 默认 30。
- M1 暂不自动删除，先记录数据规模。
- M3 增加按 `occurred_at` 分批清理任务，每批限制行数并记录日志。
- Issue 没有任何保留事件后，可按独立策略归档或删除。
- 会话回放正文不进入 MySQL，未来使用对象存储并单独设置保留期。

## 11. Flyway 规则

- 已在任何共享环境执行的 migration 永不修改。
- 每次结构变化新增 `V{n}__description.sql`。
- migration 只做确定性结构/基础数据变更，不写环境密码和演示数据。
- 破坏性迁移拆成“新增、双写/回填、切换读取、删除旧列”多个版本。
- 本地测试必须从空数据库执行全部 migration，而不是导入手工快照。

## 12. 首迁移验收

- 空 MySQL 8 数据库可以由 Flyway 一次迁移成功。
- 四张表字符集、时间精度、外键与索引符合本文。
- 相同应用不能写入重复 `event_id`。
- 不同应用允许出现相同客户端 `event_id`。
- 同一应用不能创建重复 fingerprint 的 Issue。
- JSON 列能够保存 v1 三类事件样例。
- 删除应用时相关 Issue 和 Event 行为符合外键约定。
