# M6 部署与发布设计

日期：2026-10-12。当前目标机器已改为香港 Ubuntu 22.04.5 LTS、x86_64、2 核 2GB；Docker / Compose 已安装，用户验证 hello-world 成功。原上海 OpenCloudOS 方案作废。域名 revengedog.online 需确认 A 记录已替换为香港 IP；80/443 无现有服务，SSH 可登录。发布策略：push / PR 自动 CI，CI 成功后手动选择固定 commit 部署。本文不是服务器已上线的声明。

## 1. 本轮范围

先建设个人作品演示环境，不宣称高可用或支持大规模采集。M5 回放 / 告警可以后续再做，不是上线演示的前置条件。

当前已有 CI：前端检查和构建、SDK / 发布脚本测试、后端测试、MySQL 集成测试、Playwright E2E。本轮新增生产镜像和容器检查、Caddy 入口以及手动平台发布工作流；实际 SSH、GHCR、HTTPS 与备份恢复仍待线上验收。M4 / M6 本地工作区内容还未提交，部署只能使用已推送且实际通过 CI 的代码。具体操作见 [M6首次上线与手动发布](M6首次上线与手动发布.md)。

本轮按以下顺序推进：

1. 确认操作系统版本、架构、Docker / Compose、端口和磁盘余量。
2. 配置域名解析、云安全组、HTTPS 和生产独立环境。
3. 实现并验证平台生产镜像与 Compose，部署 Console / API / MySQL。
4. 创建生产管理员和监控应用，确定生产 appId / appKey。
5. 接入 Demo 构建、Map 上传封存、公共资源发布和部署时间登记。
6. 接入 GitHub Actions 手动发布，验证一次成功发布和一次可恢复的失败。
7. 验证备份恢复、版本回退、公开 Map 隔离和外部真实访问。

## 2. 地址与网络

使用域名 revengedog.online 的两个子域名：

| 入口 | 用途 |
| --- | --- |
| https://apm.revengedog.online | Console 与同源 /api，Session Cookie 登录 |
| https://demo.revengedog.online | 被监控的生产构建 Demo |

两个 A 记录指向服务器公网 IPv4；只有 IPv6 也配置正确时才添加 AAAA。DNS、主机防火墙和云安全组需分别检查。若当前网站已占用 80/443，应接入已有反向代理，不能直接抢占端口。

域名控制台配置两条记录：类型 A，主机记录分别 apm、demo，记录值均为香港服务器公网 IPv4。首轮暂不配置根域名网站，不要求购买新域名。不保留旧上海 IP，也不使用新服务器未配置的 AAAA。

公网只发布网站入口 80/443，SSH 仅允许需要的来源。MySQL 3306 和后端容器端口不映射公网。Console /api 使用同源代理；Demo 向 APM HTTPS 地址上报，生产应用 allowedOrigins 只允许实际 Demo origin。

本轮选择 Caddy 作为静态服务和 API 反向代理，替代先前计划中的 Nginx，使用其自动证书申请与续期。证书数据持久化，Console 同源 /api，Cookie 固定 Secure。没有公网可信 HTTPS 时，发布不会被判定成功。[自动 HTTPS](https://caddyserver.com/docs/automatic-https)

参考：[Docker Compose 服务配置](https://docs.docker.com/reference/compose-file/services/)。

## 3. 2GB 服务器的约束

服务器只拉取和运行预构建产物，不运行 npm install、Vite build、Maven build 或 Playwright。构建和测试放在 GitHub 托管 runner，避免构建峰值与数据库争用内存。

首轮运行预算（待真实机器测量，不是容量承诺）：

| 组件 | 初始考虑 |
| --- | --- |
| Java | 容器约 768 MiB，堆约 384 MiB，另留 metaspace / direct buffer / 线程 / Map 解析空间 |
| MySQL | 容器约 600 MiB，小 buffer pool、有限连接数 |
| Caddy | 容器约 128 MiB |
| 宿主机与余量 | 其余留给系统、Docker 和短暂操作 |

Xmx 不等于 Java 进程总内存。必须用 docker stats、容器 OOM 状态和真实上传 / 定位请求验证限制，不因为设置了 mem_limit 就认定可以稳定运行。首轮单副本更新允许短暂维护窗口，不同时拉起两套 Java / MySQL 来宣称零停机。

生产 Hikari 连接池要适当缩小。磁盘需覆盖数据库、私有 Map、备份和保留镜像；不要盲目定时 prune volume。当前 retentionDays 是应用配置，不应在未核实清理实现前把它当成自动容量保障。

## 4. 平台和 Demo 分两阶段发布

首次发布先启动平台，原因是上传 Map 需要一个可登录的后端和真实生产监控应用。

### 平台发布

CI 成功 → 选定 commit → runner 构建 Java 与 Console 镜像 → 上传镜像仓库 → 服务器拉取 → 备份 / 迁移检查 → 更新容器 → 检查 API、登录与路由。

初次平台可以暂不发布 Demo。非开发环境没有可假定的 Demo appId=1 或 tf_app_demo_web；生产应用须新建，实际返回的 appId / appKey 用于后续构建与上传。

### Demo 发布

生产 appKey / HTTPS endpoint / commit release 注入 → 同一次压缩构建 → 登录上传 JS / Map 并封存 → 生成无 Map 的公共目录 → 发布公共文件 → 外部健康检查 → 登记 deployedAt。

Demo release 建议由完整 commit 和构建编号确定，重试必须复用相同构建的文件。如果重新构建得到不同字节，使用新版本，不覆盖已封存产物。

私有 JS / Map 留在 runner 的受控临时目录和后端私有存储，不复制进网站目录。外部实际验证 .map 和 traceflow-release.json 不可读取。仅关闭 sourceMappingURL 注释不是权限隔离。

## 5. 手动 CD 的安全边界

发布入口使用 workflow_dispatch，而不是 push 自动发布。操作者选择完整 commit SHA，流程必须核实该 SHA 属于 main 且对应 CI 已成功；不能只检查“main 最近一次 CI 成功”后部署另一个提交。

使用 GitHub production Environment 保存发布 secrets，限制允许发布的分支；有可用保护规则时开启审批。仓库权限 / 套餐是否支持相应规则需实际检查，不把 UI 中未配置的审批当作已启用。

按部署目标串行发布；不要取消一个已经开始切换服务器的发布任务。构建阶段和服务器切换阶段分开。workflow 日志不输出环境文件、密码、Cookie 或私有源码。

SSH 使用独立部署用户和密钥，并核对 known_hosts。不能用 StrictHostKeyChecking=no；ssh-keyscan 结果也要通过可信渠道核对指纹。用户不需要在聊天中提供私钥。

生产 server 文件、目标目录和服务名都固定，不接收可以任意执行远程命令的输入。镜像使用固定 SHA 标签，记录实际 digest；不使用 latest 作为发布与回滚身份。registry 访问权限单独配置，不假定私有镜像可匿名拉取。

参考：[GitHub 部署环境](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/deploy-to-environment)、[部署保护](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)。

## 6. 配置与凭证

| 配置 | 放置位置 / 约束 |
| --- | --- |
| 生产数据库账号、密码 | 服务器受限环境文件或 secrets 文件，不使用 traceflow_dev |
| 初始管理员账号、密码 | 首次 bootstrap 注入；创建后移除启动配置中的 bootstrap 密码 |
| SPRING_PROFILES_ACTIVE | 明确非 dev；不能依赖默认 dev |
| TRACEFLOW_SECURE_COOKIE | HTTPS 下 true；核实代理与 Cookie 行为 |
| TRACEFLOW_CONSOLE_ORIGINS | 实际 Console HTTPS origin，不使用宽泛通配 |
| Demo VITE_TRACEFLOW_ENDPOINT | 构建时注入实际 APM HTTPS 地址，禁止 localhost |
| Demo VITE_TRACEFLOW_APP_KEY | 实际生产应用 key，不是登录密钥，但必须对应正确应用 |
| 上传账号 | 优先生产专用发布账号；当前上传要求 admin，记录权限范围，不冒充已有最小权限 token |
| SSH / registry / 上传凭证 | GitHub Environment secrets，不提交 Git，不打进前端 JS |

生产数据库是新的独立实例，不直接复制本机带开发密码和 E2E 数据的数据库。需要迁移业务数据时另做脱敏、备份和验证方案。

## 7. 备份与回退

首次安装前明确数据库卷名和持久路径。发布不得执行 docker compose down -v。

更新前记录正在运行的镜像 digest、配置版本和数据库 schema 版本。数据库备份需覆盖事件、版本元数据和 source_maps BLOB，保存在独立受限位置，并做真实恢复测试；同服务器一份备份不等于异机容灾。

Flyway 默认启动执行前向迁移。回退旧镜像不会回退数据库；只在旧程序与当前 schema 兼容时做应用回退。破坏性 schema 变更不能自动尝试旧镜像，应停止发布并按单独恢复方案处理。

公共资源发布保留前一版并可切换。考虑打开旧页面的客户端仍请求旧 hash chunk，不能在新发布时立即清空全部旧资源。sealed Map 不随公共资源切换删除。

## 8. 服务器信息检查

提供只读脚本 deploy/preflight.sh，不安装软件、不改防火墙、不启动或停止容器。

在服务器项目文件所在目录执行：

```bash
bash deploy/preflight.sh
```

在项目尚未传到服务器时，先直接执行：

```bash
cat /etc/os-release
uname -m
docker --version
docker compose version
free -h
df -h /
ss -ltn
```

实际域名、SSH 和 80/443 空闲已确认。当前香港服务器可用内存约 1.5Gi，50G 磁盘可用约 43G、无 swap。基础软件已安装，接下来配置生产环境文件及专用发布密钥。密码、私钥、完整生产环境文件不要发进聊天。

当前 Ubuntu 使用 Docker 官方 apt 软件源安装 Engine / Compose 插件，不是 Docker Desktop，宿主机无需额外 Node / JDK。原 OpenCloudOS dnf 步骤与腾讯云大陆内网 mirror 均不适用于本轮香港部署。[Ubuntu 安装说明](https://docs.docker.com/engine/install/ubuntu/)

- 生产 Demo 真实上报，源码还原正确，Map 不公开。

- 数据库备份可恢复，数据在容器重建后仍保留。
