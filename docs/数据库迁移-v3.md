# TraceFlow 数据库迁移 V3：错误诊断与 Issue 生命周期

> 本文是 M2 的数据库迁移设计。可执行 migration 将命名为 `V3__add_issue_diagnostics.sql`，在方案确认后实现；本轮不修改数据库。

## 1. 迁移目标

V3 在现有 `issues` 和 `events` 基础上补齐：

- 指纹算法版本。
- Issue 状态变化、解决和回归时间。
- 去重后的影响 Actor 统计。
- Issue 状态历史。
- M2 查询需要的组合索引。

V3 不修改 `events.breadcrumbs`。该 JSON 列已经由 V1 创建，V2 只改变时间列类型，可以直接承载 M2 面包屑。

## 2. 延续约定

沿用 V2 的统一时间规则：

- 所有新增时间列使用 `BIGINT UNSIGNED`。
- 数值为 Unix Epoch 毫秒。
- 服务端通过 `System.currentTimeMillis()` 或事件 timestamp 写入。
- API 传递数字，Console 展示时再转换为本地时间。

其他约定：

| 项目 | 约定 |
| --- | --- |
| 数据库 | MySQL 8.4 或兼容 MySQL 8.x |
| 字符集 | `utf8mb4` |
| 存储引擎 | InnoDB |
| 摘要 | SHA-256，小写 64 位十六进制 |
| migration | Flyway 前向迁移，不修改 V1/V2 |

## 3. `issues` 表变更

### 3.1 新增列

| 列 | 类型 | 空值 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `fingerprint_version` | smallint unsigned | 否 | 1 | 生成 fingerprint 的算法版本；1 代表 M1 历史算法 |
| `status_changed_at` | bigint unsigned | 否 | 无 | 最近状态变化时间 |
| `resolved_at` | bigint unsigned | 是 | null | 最近一次进入 resolved 的时间 |
| `last_regressed_at` | bigint unsigned | 是 | null | 最近一次自动回归时间 |
| `regression_count` | bigint unsigned | 否 | 0 | 从 resolved 自动回归的累计次数 |

`fingerprint` 列和唯一约束保持不变：

```text
uk_issues_app_fingerprint(application_id, fingerprint)
```

当前不把 `fingerprint_version` 加入唯一约束。M1 历史 Issue 保持版本 1，M2 新建 Issue 使用版本 2；未来再次升级算法时必须先确定历史 Issue 合并/分裂策略，不能让同一新事件同时落入多个版本的 Issue。

### 3.2 状态约束

原约束：

```text
unresolved, resolving, resolved, ignored
```

V3 调整为：

```text
unresolved, resolving, resolved, ignored, regressed
```

迁移需要显式删除 `chk_issues_status` 后以同名重新创建。应用部署顺序要求见第 9 节。

### 3.3 回填

现有 Issue：

- `fingerprint_version = 1`。
- `status_changed_at = updated_at`。
- 当前状态为 `resolved` 时，`resolved_at = updated_at`；其他状态为 null。
- `last_regressed_at = null`。
- `regression_count = 0`。

为避免先添加 NOT NULL 列导致已有数据失败，migration 使用“可空新增、回填、改为非空”的顺序处理 `status_changed_at`。

## 4. 新表 `issue_actors`

### 4.1 用途

保存某个 Issue 下已经出现过的 Actor 摘要，保证 `affected_user_count` 按访问者去重，而不是每条事件加一。

### 4.2 表结构

| 列 | 类型 | 空值 | 说明 |
| --- | --- | --- | --- |
| `issue_id` | bigint unsigned | 否 | 所属 Issue |
| `actor_key` | char(64) | 否 | Actor 来源字符串的 SHA-256 |
| `first_seen_at` | bigint unsigned | 否 | 首次发生时间 |
| `last_seen_at` | bigint unsigned | 否 | 最近发生时间 |
| `event_count` | bigint unsigned | 否 | 此 Actor 在该 Issue 的事件数 |

主键：

```text
PRIMARY KEY (issue_id, actor_key)
```

外键：

```text
issue_id -> issues.id ON DELETE CASCADE
```

不增加独立自增 ID，因为 `(issue_id, actor_key)` 就是业务唯一键，也是 upsert 所需索引。

### 4.3 Actor key 规则

服务端按优先级构造原始值：

```text
user:{user_id}
anonymous:{anonymous_id}
session:{session_id}
```

选择第一个可用值并计算 SHA-256。`session_id` 在 v1 协议中必填，因此合法错误事件总能生成 Actor key。

数据库只存摘要，不存带前缀的原始字符串。`events` 仍按现有协议保存 user/anonymous/session 字段，以支持单次事件诊断和筛选。

### 4.4 写入语义

新错误事件写入时：

1. `INSERT ... ON DUPLICATE KEY UPDATE` 更新 Actor 的 last_seen 和 event_count。
2. 根据插入结果判断该 Actor 是否首次出现。
3. 仅首次出现时将 `issues.affected_user_count` 加一。

该操作和 Event 插入、Issue upsert 位于同一事务中。重复 `event_id` 必须在 Actor upsert 之前结束，避免重复计数。

### 4.5 历史数据回填

从已有 error events 中按 `issue_id + actor source` 分组：

- `first_seen_at = MIN(occurred_at)`。
- `last_seen_at = MAX(occurred_at)`。
- `event_count = COUNT(*)`。
- Actor 来源使用与服务端相同的 user、anonymous、session 优先级。
- 使用 MySQL `SHA2(value, 256)` 生成 `actor_key`。

回填后，将每个 Issue 的 `affected_user_count` 更新为对应 `issue_actors` 行数。没有 Event 的异常历史行保持 0。

## 5. 新表 `issue_status_history`

### 5.1 用途

记录人工状态修改和自动回归，便于详情页解释 Issue 为什么处于当前状态。

### 5.2 表结构

| 列 | 类型 | 空值 | 说明 |
| --- | --- | --- | --- |
| `id` | bigint unsigned auto_increment | 否 | 主键 |
| `issue_id` | bigint unsigned | 否 | 所属 Issue |
| `from_status` | varchar(20) | 是 | 初始记录为空 |
| `to_status` | varchar(20) | 否 | 变化后的状态 |
| `change_type` | varchar(20) | 否 | created/manual/regression/migration |
| `reason` | varchar(500) | 是 | 人工说明或系统原因 |
| `changed_by` | bigint unsigned | 是 | 管理用户；自动变化为空 |
| `changed_at` | bigint unsigned | 否 | Unix 毫秒时间戳 |

约束：

- `issue_id -> issues.id ON DELETE CASCADE`。
- `changed_by -> users.id ON DELETE SET NULL`。
- `from_status` 为空或属于合法 Issue 状态。
- `to_status` 属于合法 Issue 状态。
- `change_type` 限定为 `created`、`manual`、`regression`、`migration`。

索引：

```text
idx_issue_status_history_issue_time(issue_id, changed_at DESC, id DESC)
```

### 5.3 初始历史回填

每个现有 Issue 插入一条基线记录：

```text
from_status = null
to_status = issues.status
change_type = migration
reason = "V3 baseline"
changed_by = null
changed_at = issues.created_at
```

该记录只说明 V3 接管时的状态，不伪造历史状态变化。

## 6. `events` 索引调整

M2 Issue 详情已经可以使用：

```text
idx_events_issue_occurred(issue_id, occurred_at DESC)
```

为了让同毫秒事件分页稳定，将该索引扩展为：

```text
idx_events_issue_occurred(issue_id, occurred_at DESC, id DESC)
```

新增以下筛选索引：

```text
idx_events_app_environment_occurred
  (application_id, environment, occurred_at DESC, id DESC)

idx_events_app_release_occurred
  (application_id, release_name, occurred_at DESC, id DESC)

idx_events_app_user_occurred
  (application_id, user_id, occurred_at DESC, id DESC)
```

其中 release 和 user 索引已经存在，V3 先删除后以增加 `id DESC` 的形式重建。HTTP 状态索引保持不变。

M2 数据规模下，Issue 多条件筛选可通过 `EXISTS` 子查询关联 events。M3 引入聚合桶后再根据慢查询证据决定是否增加更多宽索引，不提前堆叠所有组合。

## 7. Issue 写入事务

目标事务顺序：

```text
插入 Event，数据库唯一键收口幂等
  -> 计算 fingerprint v2
  -> upsert Issue
  -> 查询并锁定 Issue 当前状态
  -> upsert Actor
  -> 关联 Event.issue_id
  -> 更新 latest_event_id
  -> 必要时 resolved -> regressed
  -> 写入 status history
```

并发约束：

- Event 幂等依赖 `uk_events_app_event`。
- Issue 聚合依赖 `uk_issues_app_fingerprint`。
- Actor 去重依赖 `issue_actors` 主键。
- resolved 回归时必须锁定 Issue 行或使用带状态条件的原子更新，确保并发事件只增加一次 `regression_count`。
- `latest_event_id` 只在新 Event 的 `occurred_at` 不早于当前 last_seen 时更新，迟到事件不能覆盖真正的最新事件。
- `first_seen_at = LEAST(first_seen_at, event.occurred_at)`，`last_seen_at = GREATEST(...)`。

## 8. 数据一致性规则

- `issues.event_count` 等于成功关联到该 Issue 的 Event 数量。
- `issues.affected_user_count` 等于 `issue_actors` 行数。
- `issues.latest_event_id` 指向发生时间最新的 Event；相同毫秒取较大数据库 ID。
- `resolved_at` 只在进入 resolved 时写入；离开 resolved 后保留最近一次解决时间。
- `last_regressed_at` 只在自动进入 regressed 时更新。
- `regression_count` 只计算 resolved 到 regressed 的自动转换次数。
- 删除应用时，现有级联顺序应删除 Issue、Event、Actor 和状态历史，不留下孤儿数据。

## 9. 部署兼容顺序

为了避免应用代码与 CHECK 约束不兼容，部署顺序为：

1. 停止旧服务或在本地开发环境直接停止 Java 进程。
2. 备份数据库或确认 Docker volume 可恢复。
3. 新服务启动，由 Flyway 执行 V3。
4. V3 完成后再启用可能写入 `regressed` 的 M2 代码。
5. 执行健康检查和迁移校验。

M2 当前是单实例开发环境，不设计在线双版本写入。未来生产零停机迁移应拆成“放宽约束、部署兼容代码、回填、收紧约束”多个 migration。

## 10. Migration 实现顺序

`V3__add_issue_diagnostics.sql` 计划按以下顺序执行：

1. 为 `issues` 新增可兼容列。
2. 回填 Issue 时间和指纹版本。
3. 调整 Issue 状态 CHECK。
4. 创建 `issue_actors`。
5. 从 events 回填 Actor，并重算影响人数。
6. 创建 `issue_status_history` 并写入基线历史。
7. 重建 M2 查询索引。
8. 将临时可空列收紧为 NOT NULL。

脚本必须可在以下两种数据库上执行：

- 仅执行过 V1、V2 的空业务数据库。
- 已包含 M1 Demo 事件和 Issue 的现有开发数据库。

Flyway migration 只执行一次，不要求 SQL 自身可重复执行。

## 11. 回滚策略

Flyway 已执行 migration 不直接修改或删除。

若 V3 应用后代码需要回退：

- M1 代码可以忽略新增列和新表，但不能写入旧 CHECK 不认识的状态。
- 数据修复通过新的 `V4__...sql` 前向迁移完成。
- 不使用手工 `DROP TABLE` 或修改 Flyway history 绕过校验。
- 部署前备份用于灾难恢复，不作为日常 schema 版本管理手段。

## 12. 验证清单

### 12.1 Schema

- V1 -> V2 -> V3 可从空库一次执行成功。
- 现有 V2 数据库升级成功，Flyway checksum 正常。
- 新时间列均为 `BIGINT UNSIGNED`。
- CHECK、外键和索引名称与设计一致。

### 12.2 数据回填

- 所有 Issue 的 `fingerprint_version` 为 1。
- `status_changed_at` 非空。
- 现有 resolved Issue 正确得到 `resolved_at`。
- `affected_user_count` 与 `issue_actors` 去重行数一致。
- 每个迁移前 Issue 恰有一条 migration 基线状态记录。

### 12.3 写入行为

- 同一 eventId 重试不改变 Issue、Actor 或回归计数。
- 同一 Actor 的多个错误只增加 event_count，不增加 affected_user_count。
- 不同 Actor 正确增加影响人数。
- 并发相同错误只创建一个 Issue。
- resolved Issue 并发收到多个事件时只产生一次回归状态变化。
- 迟到事件更新 first_seen，但不会错误覆盖 latest_event_id。

### 12.4 查询

- Issue 事件按 `occurred_at DESC, id DESC` 稳定分页。
- 环境、Release、用户和时间筛选结果正确。
- `EXPLAIN` 能命中预期索引，不对 events 做无约束全表扫描。

## 13. V3 完成定义

只有同时满足以下条件才认为 V3 完成：

- SQL migration 已实现并通过空库、已有数据升级测试。
- Java Entity、Mapper 和 API 字段与 schema 一致。
- Actor 去重、状态回归和历史写入由集成测试覆盖。
- `docs/数据库迁移-v1.md` 中的历史说明不被改写，V2 时间约定继续生效。
- migration 结果和 M2 错误诊断设计保持一致。
